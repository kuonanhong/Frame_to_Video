# FRAME CPU 圖片轉影片：演算法、能力與限制

本版目標是：單張照片 → 本機辨識常見物件 → 根據有限提示詞建立動畫規則 → CPU 像素變形與粒子 → 瀏覽器錄製短片。它不做生成式影片推論，也不把幾何動畫稱為 Diffusion 或 Transformer 生成結果。

## 1. OpenCV 能不能直接解決？

OpenCV 是影像處理與電腦視覺工具箱，能處理縮放、仿射變換、透視變換、光流、形態學等工作；它本身不是「能理解所有照片及提示詞」的模型。瀏覽器版 OpenCV.js 也可以部署在靜態網站，但會增加下載量，不能自動提供通用物件知識與語言理解。

本版為了控制模型與程式體積，使用 TensorFlow.js CPU 物件偵測，加上原生 JavaScript RGBA 像素算法。常見影像幾何功能不必為了名稱而載入整套 OpenCV.js。

## 2. 物件辨識：COCO-SSD lite_mobilenet_v2

附基本權重及 JavaScript CPU 推論程式，可與網站一起上傳 GitHub Pages；模型預設沒有改接雲端 API。

流程：

1. 讀取圖片並取得 RGBA 像素。
2. 在 Web Worker 內把偵測輸入等比例縮小，最大邊640像素，透明像素以白色合成。
3. 明確選擇 TensorFlow.js `cpu` 後端；只打包 CPU後端，不載入 WebGL／WebGPU推論後端。
4. 執行一次 COCO-SSD，取得分類、信心分數與 `[x, y, width, height]` 邊界框。
5. 將座標換回原圖尺度，供動畫規則使用。

COCO-SSD 可以辨識80種常見物件，但「80種」不等於「照片中所有物件」。樹、水面、天空不是完整的80類自然區域分割標籤；即使辨識到盆栽，也不代表能分割任意樹木。網頁預設信心門檻為0.45、最多8個結果（開發API預設上限20）；模型可能漏判或誤判。信心分數不是校準過的正確機率，也不是保證物件位置精確。

邊界框只圈出矩形。背景、其他物件與不透明空隙可能一起在框內，不能稱為精細語意分割。水、樹、雲及想單獨變形的區域，需要使用者人工圈選。本版沒有姿態估測、人物骨架、遮擋重建或背景補畫模型。

## 3. 提示詞：有限規則而不是大型語言模型

`motion-core.mjs` 的 `parsePrompt()` 以關鍵字與物件類型建立計畫。支援的動作包括：

| 動作 | 對應做法 | 條件 |
|---|---|---|
| 鏡頭推近／拉遠 | 等比例裁切尺寸隨時間改變 | 可作用整張圖 |
| 鏡頭向左／右／上／下 | 在可裁切範圍內改變畫面中心 | 必要時稍微放大，避免露出不存在的邊緣 |
| 搖擺 | 區域內的水平位移隨高度變化 | 已供應物件框或手動畫框 |
| 上下浮動 | 區域內的正弦垂直位移 | 船、鳥或人工雲區域等已知規則 |
| 輕微呼吸 | 區域內小幅中心縮放 | 人物、貓、狗、鳥等已知規則 |
| 水波 | 手動水面區域的二維正弦位移 | 必須人工標示水面 |
| 雨／雪 | 固定種子產生粒子位置並逐幀疊加 | 不必有物件辨識框 |

提示詞例：「小船漂浮，水面波紋，鏡頭慢慢拉近」需要照片中有可用船框與人工水面區域。沒有供應區域時會提示缺少區域，不會只因文字提到船、水或樹就發明影像內容。

核心詞表目前主要涵蓋繁簡中文、英文，以及部分日、韓、法、德、西班牙語。22語介面不表示22語任意長句都能解析；其他語言可用效果按鈕或已支援的英文短語。這種有限詞表不能完整理解否定、條件、故事或複合語意。例如「不要下雪」中的「下雪」可能仍觸發詞規則；請用按鈕或直接刪除不需要的描述。對相反方向、無區域與明顯未支援動作，摘要會提供限制提示。

不支援的語意包括：人真的走路、動物自然飛翔、人物轉身、張嘴說話、新增不存在的物體、移除物件並補回背景、改成另一個人物。這些不是可靠的單圖幾何規則能完成的任務。

## 4. 保持比例的鏡頭變換

令來源尺寸為 \(W_s,H_s\)，輸出比例為 \(a=W_o/H_o\)。先選擇能填滿畫面的等比例裁切框：

- 若 \(W_s/H_s>a\)，取 \(H_c=H_s\)、\(W_c=aH_s\)；
- 否則取 \(W_c=W_s\)、\(H_c=W_s/a\)。

縮放倍率 \(z(t)\) 增加時，用 \(W_c/z(t),H_c/z(t)\) 取樣。時間以 smoothstep 平滑：

\[
p=t/T,\qquad s(p)=3p^2-2p^3,\qquad 0\le p\le1.
\]

鏡頭中心只在現有來源像素範圍內移動，取樣使用雙線性插值。這樣不會像直接把任意寬高照片 resize 成1080×1920那樣改變人物比例，但會裁掉部分邊緣。

## 5. 局部變形與近似遮罩

對輸出像素反推來源位置，再以小幅位移取樣；不需要重新生成整張圖。以波紋為例，局部正規化座標 \(u,v\) 的位移近似為：

\[
\Delta x=A_x\sin(6\pi v+2\pi p),\qquad
\Delta y=A_y\sin(4\pi u-2\pi p).
\]

搖擺使用接近頂部較大的水平位移，底部較小；上下浮動與呼吸使用不同的位移或縮放規則。矩形邊緣以 feather／smoothstep 混合，減少突兀邊界。這些是視覺近似，不是流體、布料、肌肉或剛體運動的完整物理模擬。

取樣會夾在選取框內，沒有背景生成或遮擋補畫；大位移可能重複邊緣像素並造成不自然形變。因此本版限制振幅與區域數，適合細微照片動畫，不能要求大幅運動及可信的三維旋轉。

## 6. 為何不是「單圖真正光流」

光流描述影格間的影像運動。只有一張照片時，沒有觀測到下一張影格，真實速度場無法唯一決定。可以按照正弦函數或指定場產生像素變形，但應稱為「合成位移場／像素變形」，不能稱為已測量的真實光流。

MiDaS等單目深度模型屬於神經網路，可用CPU推論，但依然需要模型、記憶體和計算；它也不能可靠恢復所有遮住的表面。INT8量化通常需要相容的後端與校準驗證，不是把所有FP32模型改一個參數就能高速執行。本版沒有附MiDaS或實際2.5D深度模型，請不要把鏡頭裁切稱為完整的3D視差重建。

## 7. CPU 成本與邊緣裝置

辨識在每張照片第一次需要時執行，並放在Worker，避免把一次重推論放入每個動畫影格。動畫依輸出像素逐幀運算，大致隨：

\[
\text{工作量}\propto W_oH_o\times F\times T\times(1+R)
\]

增加，其中 \(R\) 是作用區域數；實際區域相交、函數運算與編碼成本也有影響。本版重用影格緩衝區，對輸入與輸出大小、區域與粒子數設限制。這些限制降低耗用，不能保證任何手機都能即時跑720p。

「幾毫秒完成」「低功耗MCU也能直接完整辨識及編碼」沒有通用保證。例如480p RGBA一幀已約1.6 MB，COCO-SSD還要模型權重與中間tensor；許多MCU的RAM不足。真正MCU方案通常需要更小模型、專用DSP／NPU、外部RAM，或只做低解析度簡單動畫。本套件以具有現代瀏覽器的電腦與手機為目標。

OpenCV可用SIMD最佳化，例如ARM NEON、x86 AVX，但這屬CPU指令集，不等於專用影片編碼器。Intel Quick Sync則屬硬體媒體功能，不能被描述為嚴格的「純CPU軟體編碼」。本版使用瀏覽器MediaRecorder，無法要求所有作業系統用同一編碼器；若嚴格要求軟體CPU編碼，可另在本機FFmpeg使用libx264，但不包含於這個瀏覽器免費工具流程。

## 8. 免費與並發邊界

模型與原創程式附在靜態套件，不依賴付費API；每位訪客的照片與渲染在自己的分頁完成。這讓多人運算彼此獨立，但模型下載與靜態檔案仍由同一網站/CDN提供。十萬名首次訪客會帶來大量總下載流量，因此需要容量估算與服務商限額查核，不能以「不需要後端」推導「十萬人不會crash」或「永遠無限免費」。

沒有後端也表示沒有中央影片雲端儲存、帳號同步或共用排程。下載的影片與儲存的單幀由使用者自己保存。
